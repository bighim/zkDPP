\paragraph{기호 모델의 검증 방법.}

\ref{sec:analysis}절의 일반 논증과 별도로, 객체·감사 기록·집행 식별자의 연결을
유한한 실행 사례에서 검사하였다. 보조 자료의 Python 3 프로그램
\texttt{model\_check.py}는 입출력 타입, 정수 회계, 유일 소비 기록과
감사 배열을 표현하는 기호 모델이다. 암호문은 평문의 타입·위치
대응으로 추상화하고, 식별자는 서로 구별되는 기호로 둔다.
암호화·영지식증명·역할 인증·RPC 인증을 구현한 프로그램은 아니다.
정책 선택, 문서 결합과 키 전달의 실제 집행도 이 검사 범위 밖이다.

검사할 추적 알고리즘은 생성 기록 색인, 감사 평문 슬롯과 타입별
소비 색인을 읽는다. 독립 기대값은 같은 사례의 원래 입력·출력
목록에서 만든 간선 집합에 고정점 도달 계산을 적용하여 구한다.
이 계산은 감사 슬롯이나 소비 색인을 읽지 않는다. 두 경로가 반환한
객체·이벤트 정점, 간선과 타입별 미소비 집합을 대조한다.
따라서 두 계산은 같은 사례를 서로 다른 경로로 해석한다.
유효 관계의 가정 자체나 모든 가능한 이력에 대한 암호 보안을
입증하는 검사는 아니며, 공통 사례 자료의 오류 가능성도 남는다.

네 사례군은 생산·이전·가공·발급, 분기 후 재합류·종료,
이전 증표 회수, 질량 0 출력의 탄소 배분이다.
각 사례의 비어 있지 않은 모든 접두 이력에서 존재하는 모든 객체와
이벤트를 시작점으로 선행·후속 추적을 대조하였다.
총 334개 추적 비교에서 두 계산의 정점·간선·미소비 집합이 같았다.
검사한 네 사례 안에서는 모든 시작점과 해당 시점을 대조했다.
그러나 만들 수 있는 모든 이력과 상태 변화를 검사한 것은 아니다.

두 계산이 일치해도 명세의 모든 규칙을 확인한 것은 아니다.
둘 다 기록에서 시작할 때 어떤 점과 화살표를 결과에 넣는지에 관해
명세와 다른 규칙을 사용한다. 예를 들어
$\mathit{Entry}\ e\to a$에서 모델의 후속 결과는 $e,a$와 출력
간선을 포함하나 명세는 $a$만 포함한다. 기록에서 시작하는 선행
추적에서는 모델이 $e$만 포함하나 명세는 $e,a$와 출력 간선을 포함한다.
따라서 334건은 두 모델 계산의 일치를 나타내며 명세의 시작점 처리
전체를 검증한 수치는 아니다.

\paragraph{생산·이전 사례의 추적과 차단.}

Fig.~\ref{fig:worked-flow}는 처음에는 정상으로 받아들인 원료의
증빙에 나중에 문제가 발견된 가상 사례다.
입력 $A$에서 시작해 어느 기록이 남는지 순서대로 살펴본다.
각 괄호의 세 수는 질량, 재활용 크레딧, 탄소 값이다. $A$의 $(q,a,e)=(12,6,12)$를
같은 값 $(6,3,6)$의 $B,C$로 분할한다. $B$를 전량 이전하고
운송 탄소 2를 더하면 이전 증표 $V=(6,3,8)$과 잔여 회계 증표
$Z=(0,0,0)$가 생긴다. 수신자는 $V$를 같은 회계 값의 $D$로
인수한다. 별도 등록한 $X=(2,1,2)$와 $D$를 가공하고 공정 탄소
1을 더하여 일반용 $E=(7,4,11)$과 폐기물 $W=(1,0,0)$를 만든다.
다른 분기의 $C$는 이미 제품 주장 $K$로 발급되었다고 둔다.

이 시점에 $A$에서 후속 추적을 하면 $Z,E,W$가 전체 미소비
대상이다. $X$는 합류한 이벤트의 다른 부모이므로 후속 추적이
그 선행 경로를 역으로 확장하지 않는다. $K$는 감사 결과의 종단으로
남지만 상태 변경 대상은 아니다. $Z$는 질량이 0이고 $W$는
폐기물이지만 종료로 소비할 수 있어 대상에서 제외하지 않는다.
셋을 차단하면 $E$의 추가 가공·이전·발급 및 $Z,W$의 종료도
현재 상태 검사에서 거부된다. 이와 별도로 등록한 정상 객체 $Y$는
차단 대상에 포함되지 않는다.

기준 시점을 $V$의 인수 이전으로 옮기면 대상은 $C,V,Z$이다.
그 이후 $V$의 인수가 동결보다 먼저 수락되면, 이전 기준의 실행은
$V$를 제거하여 완료를 보고하지 않고 소비 경합으로 남긴다.
새 기준의 후속 감사는 $D$ 이후의 현재 대상을 조사한다.
이 사례에서 이미 발급된 DPP는 이력으로 남는다.
사용을 제한하는 대상은 아직 남아 있는 생산·이전 기록이다.

\paragraph{실패 상황과 기호 검사 결과.}

Table~\ref{tab:model-cases}는 동일 모델에서 실행한 추가 검사를
요약한다. 모든 소비 이벤트 종류에 대해 유효한 사례의 입력 하나를
동결 또는 사용 금지 상태로 바꾸어 해당 소비가 거부되는지 확인했다.
인수·회수는 같은 이전 증표의 동일 식별자를 사용하며, 어느 경로를
먼저 수락해도 다른 경로를 같은 상태에서 다시 수락할 수 없었다.
불명확한 제출, 대상 누락, 부분 동결과 소비 경합은 전체 완료로
판정되지 않았다. 오류를 삽입한 감사 조회는 실패로 끝났으며,
자료가 없다는 응답을 미소비라는 인증된 응답으로 대체하지 않았다.

완료 검사는 소비·상태 전이를 실제로 순서대로 적용하고 각 시점의
상태를 보존하는 별도 이력 모델에서 수행했다. 감사 실행의 대상과
$H_t$는 추적을 수행한 스냅샷에 고정하며, 결과의 관찰 시점과
$H_r$도 같은 이력에서 얻는다. 예를 들어 $H_8$의 대상
$\{E,W,Z\}$를 차례로 동결하면 $H_{11}$에서 완료할 수 있지만,
같은 대상을 존재 이전인 $H_1$에서 완료했다고 보고할 수는 없다.
다른 실행에서 $E$를 동결하고 해제한 뒤 $W,Z$를 동결하면
세 성공 영수증이 있어도 전체가 동시에 차단된 스냅샷이 없었다.
이 실행은 미완료로 남고, $E$의 재동결 제출을 실제 수락한 뒤에만
완료로 바뀐다. 상태 변경 로그를 별도로 재생하여 저장된
상태와도 대조하였다. 이 로컬 시점 연결은 외부 합의·RPC 인증의
구현이나 모든 경합 순서에 대한 전수 검증을 대신하지 않는다.

전체 407개 확인 항목에는 334개 추적 대조, 선택한 실패 사례와
순차 상태·경합 실행, 소비 상태 검사와 두 인터페이스·회계 반례가 포함된다.
여기서 반례는 강한 주장이 성립하지 않는 실행 예다.
반례의 ``통과''는 취약한 조건이 안전하다는 뜻이 아니라,
주장한 허용 실행 또는 가정 누락의 결과가 재현되었다는 뜻이다.
예를 들어 질량 0 출력에 탄소 잔여가 귀속되는 사례는
\ref{sec:limits}절의 한계와 동일한 값으로 재현된다.

보조 자료에는 사례 정의, 프로그램, 실행 명령과 원시 JSON 결과를
포함한다. \texttt{python3 model\_check.py --output results.json}으로
재실행할 수 있다. 실행은 무작위 표본을 사용하지 않으며, 결과에는
소스 해시와 각 확인 항목을 남긴다. 검사 범위는 기호 모델의
관계와 실행 결과이며, 같은 의무를 구현한 조합 기준선
$C^\star$가 같은 검사를 통과하는 것과 양립한다.
