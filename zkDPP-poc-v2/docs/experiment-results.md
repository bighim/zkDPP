## 1. 기본 성능

**기본 설정**  
State는 3개입니다.  
Audit을 사용합니다.  
Process의 기본 입출력은 2→1입니다.  
Issue에는 Standard Policy를 사용합니다.  
  
**반복 기준**  
입력 Note·path·Policy를 확보한 뒤 측정을 시작합니다.  
각 case는 warm-up 1회 후 공식 5회 실행합니다.  
표에는 공식 5회의 **median**을 표시합니다.

**Event E2E**  
참여자가 해당 Event의 witness를 준비할 때부터 측정합니다.  
Proof를 생성하고 transaction을 구성·제출합니다.  
성공 receipt를 확인하면 측정을 끝냅니다.  
로컬 Verify와 사후 상태 대조는 이 시간에서 제외합니다.  
  
**Gas**  
해당 Event를 제출한 계정의 실제 Anvil transaction **gasUsed**입니다.  
온체인 Proof 검증과 상태 변경 비용을 포함합니다.  
Contract 배포 비용은 포함하지 않습니다.

### 제3자의 DPPClaim 확인 비용

**확인 대상**  
제3자는 제시된 문서·Policy가 온체인에 등록된 DPPClaim과 일치하는지 확인합니다.  
  
**측정 범위**  
확인 함수를 호출하면 Snapshot을 확보합니다.

## 2. 추가 기능 비용

### 직접 전달과 Voucher 전달·반환

**고정 조건**  
세 경로 모두 Audit을 사용하지 않습니다.  
입력 State·전달량·운송 탄소·Change 규칙을 동일하게 맞췄습니다.  
  
**비교 경로**  
직접 Transfer는 Receiver Note를 바로 생성합니다.  
Transfer → Proceed는 Voucher를 거쳐 Receiver Note를 생성합니다.  
Transfer → Recall은 Voucher를 거쳐 Sender에게 Note를 반환합니다.  
  
**경로 E2E**  
첫 Transfer의 witness 준비부터 측정합니다.  
직접 전달·수령·반환 중 해당 경로의 마지막 성공 receipt에서 끝납니다.  
로컬 Voucher 전달과 최신 path 확보도 포함합니다.  
  
**총 Gas**  
해당 경로에서 실제 실행한 모든 transaction의 gasUsed를 합산합니다.

| 경로 | tx 수 | 총 Gas | 경로 E2E (ms) |
|---|---:|---:|---:|
| 직접 Transfer | 1 | 2,366,228 | 1,590.033 |
| Transfer → Proceed | 2 | 4,742,647 | 2,083.039 |
| Transfer → Recall | 2 | 4,744,093 | 2,296.865 |

**Voucher를 사용하면 Proof와 transaction이 한 번 더 필요합니다.**  
그 대신 Sender가 Recall로 반환받는 경로를 제공합니다.  
직접 전달에는 Recall에 대응하는 동작이 없습니다.  
따라서 Recall의 비용은 동일 기능의 증가율이 아니라 추가 기능의 비용으로 봅니다.

## 3. 확장성

### Tracing 기록 수·분기 구조와 Freeze 비용

**시간 단위는 초(s)**입니다.  
  
**시작점과 대상**  
Forward는 최초 cm에서 시작합니다.  
Backward는 가장 깊은 최종 Note에서 시작해 조상을 찾습니다.  
두 Tracing은 복구된 Master Key와 확보한 Snapshot을 사용합니다.  
각각 Tracing을 시작해서 완료할 때까지 측정합니다.  
키 복구와 Snapshot 확보 시간은 두 열에 포함하지 않습니다.  
대상 수는 동결할 미소비·Active Note/Voucher의 수입니다.  
  
**Freeze와 전체 시간**  
Freeze는 이미 찾은 대상의 동결 처리를 시작할 때부터 측정합니다.  
제출 전 상태 검사와 동결 transaction 실행을 포함합니다.  
공통 Snapshot에서 최종 상태를 확인하면 끝납니다.  
전체는 Master Key 복구부터 시작하는 **AuditAndFreeze** 시간입니다.  
Snapshot 확보 → Forward → Freeze → 최종 확인을 포함합니다.  
Backward는 전체 시간에 포함하지 않습니다.

| 구조 | 기록 수 | 대상 수 | Forward | Backward | Freeze | 전체 |
|---|---:|---:|---:|---:|---:|---:|
| 연속 Split | 10 | 10 | 0.067 | 0.068 | 0.220 | 0.310 |
| 연속 Split | 100 | 100 | 0.681 | 0.554 | 2.448 | 3.059 |
| 연속 Split | 1,000 | 1,000 | 9.760 | 8.102 | 60.540 | 72.137 |
| 균형 Split | 10 | 10 | 0.075 | 0.030 | 0.220 | 0.302 |
| 균형 Split | 100 | 100 | 0.716 | 0.047 | 2.424 | 3.179 |
| 균형 Split | 1,000 | 1,000 | 10.024 | 0.072 | 63.007 | 73.372 |
| Split → Merge | 11 | 1 | 0.077 | 0.092 | 0.032 | 0.121 |
| Split → Merge | 101 | 1 | 0.640 | 0.683 | 0.027 | 0.738 |
| Split → Merge | 1,001 | 1 | 9.435 | 9.425 | 0.060 | 9.802 |

**비교 방법**  
같은 구조의 행끼리 비교하면 기록 수 증가의 영향을 볼 수 있습니다.  
같은 기록 수에서 연속 Split과 균형 Split을 비교하면 분기 구조의 영향을 볼 수 있습니다.  
Split → Merge는 11/101/1,001개입니다.  
다른 두 구조의 10/100/1,000개와 정확히 같은 기록 수는 아닙니다.  
  
**반복 조건**  
각 감사는 빈 cache에서 시작합니다.  
같은 graph의 읽기 전용 Tracing은 고정 Snapshot에서 반복합니다.  
Freeze는 매회 대상들을 같은 미소비·Active 상태로 되돌린 뒤 실행합니다.  
graph 구축과 Proof 준비 시간은 제외합니다.  
  
**해석할 때 주의할 점**  
Backward는 전체 기록이 아니라 시작 Note의 조상만 방문합니다.  
각 열은 따로 측정한 시간의 median입니다.  
따라서 각 열을 더한 값이 전체 시간과 같지는 않습니다.

### Process 입출력 Note 수 증가 — E2E (ms)

**E2E**  
각 구성의 Process witness 준비부터 성공 receipt 확인까지입니다.  
시간은 Constraints·gas와 함께 보는 보조 지표입니다.

| 입력→출력 | Audit 없음 | Audit 있음 |
|---|---:|---:|
| 2→1 | 1,135.004 | 1,145.325 |
| 2→2 | 1,278.742 | 2,019.486 |
| 3→2 | 2,012.802 | 2,086.724 |
| 3→3 | 2,175.972 | 2,252.832 |
| 4→3 | 2,241.576 | 2,271.843 |

**domain 변화**  
Process 2→2에서 Audit을 추가하면 domain이 65,536에서 131,072로 커집니다.  
이 값은 PLONK가 사용하는 계산 영역의 크기입니다.  
따라서 Constraints 증가율이 실제 시간 증가율과 같을 필요는 없습니다.  
  
**결과의 출처**  
위 세 표는 입출력 확장 실험에서 별도로 측정한 결과입니다.  
1장의 기본 성능 표와 같은 실행을 다시 집계한 값이 아닙니다.

## 4. 암호화 세부 비용

### 복호화할 AuditRecord 수 증가

**고정 조건**  
암호문 한 개에 Field 3개를 넣습니다.  
Master Key 복구와 암호문 생성은 측정 전에 끝냅니다.  
  
**변경 조건**  
복호화할 암호문 수를 1·10·100·1,000개로 늘립니다.  
  
**전체 복호화 시간**  
Auditor가 해당 행의 암호문을 모두 복호화한 시간입니다.  
암호문 한 개의 평균 시간이 아닙니다.  
RPC 조회 시간은 포함하지 않습니다.

### AuditRecord 한 건의 암호화 정보량 증가

### Master Key 복구에 사용하는 share 수 증가

**고정 조건**

### 동일한 share 수로 복구할 때 전체 Committee 수 증가

**고정 조건**  
복구에는 항상 share 2개를 사용합니다.  
  
**변경 조건**  
전체 Committee 수 n을 3·5·10·20으로 늘립니다.  
n이 늘어나면 package에서 검사할 위원 정보도 많아집니다.  
  
**복구 시간**  
package 검사부터 Master Key 복구·공개키 대조까지 측정합니다.  
복구에 사용한 share 수가 늘어난 결과는 아닙니다.  
DKG·위원 통신·승인 대기는 제외합니다.

| Committee n | 복구 (ms) |
|---:|---:|
| 3 | 0.433 |
| 5 | 0.565 |
| 10 | 0.898 |
| 20 | 1.550 |

**짧은 작업의 반복 방법**  
각 공식 run에서 해당 workload를 1,000회 실행합니다.  
반복 전체 시간을 1,000으로 나누어 workload 한 번의 시간을 구합니다.  
이렇게 얻은 공식 run 5개의 median을 표에 표시합니다.  
  
**중복된 조건**  
두 복호화 표의 암호문 1개·3 Field 조건은 같은 측정값입니다.  
두 키 복구 표의 2-of-10 조건도 같은 측정값입니다.

## 환경·한계·원자료

**증명 환경**  
Go 1.25.7, gnark 0.15.0, gnark-crypto 0.20.1을 사용합니다.  
Proof system은 PLONK-KZG/BLS12-381입니다.  
암호화에는 Jubjub·Poseidon2를 사용합니다.  
GOMAXPROCS는 8입니다.  
  
**온체인 환경**  
Anvil 1.7.1, Solidity 0.8.30, Prague를 사용합니다.  
chain ID는 31337이고 gas limit은 30M입니다.  
  
**State 표기**  
State 순서는 질량·재활용 질량·탄소입니다.  
구현에서는 각 값을 10^9 scale 정수로 처리합니다.

**준비 비용**  
development SRS 131,075 points를 생성하는 데 1667.927 ms가 걸렸습니다.  
41개 relation의 PK·VK를 생성했습니다.  
Setup과 배포는 Event E2E에 포함하지 않습니다.  
준비 작업은 공식 case처럼 5회 반복한 값이 아닙니다.

**실패와 재실행**  
최초 Tracing 실행은 Docker 메모리 부족(OOM, exit 137)으로 실패했습니다.  
실패 기록은 그대로 보존했습니다.  
재실행에서는 step tracing을 끄고 graph마다 새 노드를 사용했습니다.  
다른 실험과 계측 설정이 다르므로 절대시간을 직접 비교하지 않습니다.

**해석 범위**  
이 결과는 Anvil에서 구성한 graph의 실험값입니다.  
Production finality나 동시 처리량을 입증하지 않습니다.  
DKG와 안전한 키 폐기도 이번 측정 대상이 아닙니다.  
Privacy 보장을 성능값으로 증명하지 않습니다.  
기존 M1-HF와 v1 결과는 재측정하지 않았습니다.
