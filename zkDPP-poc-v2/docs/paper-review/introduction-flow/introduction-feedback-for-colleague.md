# Introduction에 포함되면 좋을 내용

현재 Introduction은 문제가 발생한 이후의 추적과 Freeze를 자세히 설명하고 있다고 느꼈습니다.  
여기에 아래 내용이 함께 들어가면, **zkDPP가 공급망에서 어떤 문제를 다루고 왜 필요한지**가 더 잘 전달될 것 같습니다.

## 1. Privacy를 유지하면서 Sustainability Claim을 검증하려는 목적

**기업의 상세 정보를 공개하지 않으면서, 생산·이전 과정의 계산과 최종 Sustainability Claim을 검증하려는 시스템**이라는 설명이 들어가면 좋겠습니다.  
원료가 이전·분할·병합·가공되는 동안 제품의 환경정보가 어떻게 계산됐는지 확인하고, 그 결과를 제품의 Claim에 연결하려는 것이 연구의 출발점이라고 생각합니다.

탄소배출량이나 재활용 함량에 관한 주장에 충분한 근거가 없으면 소비자가 제품을 잘못 판단할 수 있다는 배경도 함께 있으면 좋겠습니다.  
EU 집행위원회도 근거가 부족하거나 소비자에게 잘못된 인상을 주는 환경 주장을 Greenwashing 문제로 설명하고 있습니다.  
이 배경이 있으면, 최종 제품에 표시된 수치뿐 아니라 **그 수치를 만들 때 사용한 자료와 계산 과정도 확인해야 하는 이유**가 자연스럽게 드러날 것 같습니다. [출처](https://environment.ec.europa.eu/topics/circular-economy-topics/green-claims_en)

## 2. 정기 감사에 더해 Event가 발생할 때마다 계산을 확인한다는 설명

ISCC처럼 정기 감사와 추가 점검을 운영하는 사례와 함께, **생산·거래가 계속되는 동안에도 새 정보와 변화를 확인할 필요가 있다**는 배경이 들어가면 좋겠습니다.  
OECD도 공급망 실사를 일회성 확인이 아니라 지속적인 과정으로 설명하며, 신규 제품이나 사업 관계의 변화에 맞춰 다시 평가하도록 권고합니다. [ISCC](https://iscc-system.org/iscc-integrity-programme-for-a-more-robust-certification-system/) · [OECD, 제I부 및 제II부 2.2(g)](https://www.oecd.org/content/dam/oecd/en/publications/reports/2018/02/oecd-due-diligence-guidance-for-responsible-business-conduct_c669bd57/15f5f4b3-en.pdf)

Split·Merge에서는 입력 State를 정해진 규칙에 따라 나누거나 합치므로, 출력에 원하는 값을 임의로 붙일 수 없다는 설명이 있으면 좋겠습니다.  
반면 Entry의 최초 정보가 실제 물품과 맞는지, Process의 공정 규칙과 새로 반영할 정보가 적절한지는 외부의 확인이 필요합니다.  
이 구분을 보여주면 **제3자가 확인해야 할 사실과 시스템이 반복해서 검사할 계산**이 무엇인지 이해하기 쉬울 것 같습니다.

제3자가 초기 자료와 공정 규칙의 적절성을 확인하고, 시스템은 승인된 규칙을 **Entry·Process를 포함한 각 Event가 발생할 때마다 검증한다**는 흐름이 들어가면 좋겠습니다.  
그러면 다음 정기 감사까지 기다리지 않고, 규칙에 맞지 않는 State 계산을 해당 거래가 수락되기 전에 거부할 수 있다는 장점이 드러납니다.  
이는 제3자가 매 거래마다 현장 감사를 한다는 뜻이 아니라, **외부의 확인을 바탕으로 거래별 계산 검증을 수행해 정기 감사를 보완한다**는 의미입니다.

## 3. 공급망 이전에서 Recall이 필요한 상황

기존 설계 논의에 있었던 미지급, 잘못 지정한 수신자, 잘못 입력한 탄소량·재활용률·수량 등의 상황도 Introduction에 간단히 들어가면 좋겠습니다.  
이런 사례가 있으면, 정보를 비공개로 전달하는 것뿐 아니라 **허용된 기간 안에 아직 인수가 확정되지 않은 이전을 보낸 사람이 되돌릴 수 있는 기능**이 왜 필요한지 이해할 수 있을 것 같습니다.

여기서는 실제 제품의 리콜이나 이미 완료된 거래 전체의 취소가 아니라, **인수가 확정되기 전의 이전을 되돌릴 필요성**에 초점을 두면 좋겠습니다.  
그렇게 하면 회수 기능이 필요한 이유를 설명하면서도, 대금 지급이나 실물 반환까지 자동으로 처리한다는 오해를 줄일 수 있을 것 같습니다.

## 4. 양방향 Traceability의 필요성과 정보 공개의 부담

**완제품에서 사용된 원료와 공정을 조사하는 경우와, 특정 원료가 사용된 후속 기록을 찾는 경우**가 함께 들어가면 좋겠습니다.  
전자는 Backward Tracing, 후자는 Forward Tracing이 필요한 상황이며, 모든 감사가 곧바로 Freeze를 목적으로 하는 것은 아니라고 생각합니다.

Sahai 등의 Introduction은 제품 출처와 오염 관련 추적의 필요성을 설명하면서, 같은 공급망에 경쟁자가 참여하므로 민감한 사업정보의 공개가 부담된다는 점도 다룹니다.  
분할·병합·가공처럼 제품과 기록의 관계가 복잡해지는 과정까지 고려해야 한다는 설명도 있습니다.  
이러한 배경을 함께 제시하면, **상세 연결을 누구에게나 공개하지 않으면서 승인된 Auditor는 추적할 수 있어야 한다는 요구**가 자연스럽게 전달될 것 같습니다. [논문 소개](https://research.ibm.com/publications/enabling-privacy-and-traceability-in-supply-chains-using-blockchain-and-zero-knowledge-proofs)

이러한 배경과 필요성을 먼저 설명한 뒤 기존의 Freeze 내용으로 이어지면, **공급망 정보를 검증하고, 필요한 이력을 조사하며, 사용 중단이 결정되면 후속 사용을 막는 전체 흐름**이 더 잘 보일 것 같습니다.  
Contribution에서는 앞서 제시한 요구를 zkDPP가 어떻게 충족하며 무엇을 실제로 확인했는지 정리하면 좋겠습니다.
