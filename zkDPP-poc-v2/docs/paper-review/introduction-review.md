# 서론 검토 — 대화용 쟁점

대상: `zkdpp-v0.2-260916.pdf` 원본 1–2쪽.
`zkdpp-v0.2-260916-introduction.tex`는 원문 보존용 전사본이다.
아래는 수정 확정안이 아니라 함께 검토할 질문이다.
서론의 표현·논리 흐름을 검토했으며, 보안 증명 전체의 타당성이나 인용 문헌·법령의 정확성을 검증한 결과는 아니다.

## 전체 흐름

```text
1.1 DPP 정보의 근거를 공급망 단계에서 검증해야 한다.
    상세 수치와 기업 간 연결은 공개하기 어렵다.
1.2 입력 근거에 사후 문제가 생기면, 현재 후속 객체의 사용도 제한해야 한다.
1.3 검증·발급·추적·차단이 같은 이력을 가리키도록 연결해야 한다.
1.4 zkDPP의 구성과 조건부 보장을 제시한다.
```

문제 → 사후 대응 필요성 → 연구 과제 → 제안의 순서는 자연스럽다.
특히 "자료가 틀려도 계산은 규칙에 맞을 수 있다"는 구분은 연구 필요성을 설명하는 좋은 연결이다.

## 우선 확인할 논문 범위

Abstract 마지막: "구체 암호 방식의 가정 충족과 구현 적합성·성능은 검증하지 않았다."

현재 초안은 시스템 구성·조건부 증명·기호 모델 검사를 기여로 삼는다.
우리가 진행한 POC 실험을 포함할 계획이라면 이 문장과 기여 목록을 다시 정해야 한다.
단순히 이 문장을 삭제하는 것은 부족하다. 이 논문의 키 구조·Event·회계 규칙과 POC가 일치하는지 먼저 확인해야 한다.

1.4의 "감사 데이터의 복호화 키는 … 임계 암호화로 감싸 보호"는 key wrapping을 기술한다.
최근 실험의 한 단계 Master Key share 복구와 동일하다고 가정해서는 안 된다.
어느 쪽이 목표 설계인지 이 전사 작업에서는 결정하지 않는다.

## Abstract

- **핵심 문제는 보인다.** 비공개 입력 연결 때문에 후속 사용 제한 대상을 알아내기 어렵다는 문제와, 감사 정보의 proof binding이라는 접근이 연결된다.
- **첫 독자에게 낯선 말이 많다.** "원료의 인정 근거", "후속 회계 객체", "집행 식별자", "명시적 계약", "두 키 암호화"가 정의 전에 연속 등장한다.
- **법적 계약/Smart Contract/암호 인터페이스를 구분해야 한다.** 여기서 "명시적 계약"이 무엇인지 Abstract만으로 불명확하다.
- **기여 대비 한계 설명의 비중이 크다.** 제한을 없애자는 뜻이 아니라, 해결한 문제·구성·확인한 결과가 먼저 읽히는지 검토할 필요가 있다.
- **영문과 국문 범위 비교 필요.** 영문은 암호화된 부모 참조를 명시하지만 국문 해당 문장은 암호화를 생략한다. 내용상 모순이라고 단정할 수는 없으나 두 Abstract가 같은 구성을 전달하는지 확인한다.

## 1.1 제품정보의 신뢰성과 공급망 근거

- **좋은 구분:** 증빙 발급의 유효성과 후속 계산의 타당성을 별도 문제로 둔다.
- **"근거를 배분한다"의 대상:** 증빙 문서를 나누는지, 재활용량·탄소 같은 회계 수치를 배분하는지 명확히 할 필요가 있다.
- **구체 예시의 부재:** 한 원료를 둘로 나눌 때 어떤 값이 어떻게 이어지는지 한 문장 예시가 있으면 연구 대상이 더 선명해진다.
- **실물과 디지털 객체의 경계:** 독자가 이력 검증을 실제 원료의 진위·함량 보장으로 읽지 않도록 짧은 경계 설명을 어디에 둘지 논의한다. Abstract에는 물리적 회수의 제외가 있지만 실물 입력의 진실성과는 다른 문제다.
- **"검증하는 권한"의 의미:** 공개 검증 가능성을 말하는지, permissioned verifier 자격을 말하는지 확인해야 한다.
- **규정의 역할:** DPP의 정보 의무가 제안한 전체 descendant Freeze를 요구한다는 뜻으로 읽히지 않도록 동기와 설계 선택을 분리한다. 법적 요구 자체의 검증은 별도 작업이다.

## 1.2 정상 검증을 보완하는 사후 대응

- **가장 설득력 있는 연결:** "자료에 오류가 있더라도 그 자료를 사용한 계산은 규칙에 맞을 수 있다."
- **"적용돼야 한다"의 범위:** 모든 후속 객체를 차단하는 것은 시스템의 보수적인 대응 정책인가? 영향량에 비례한 차단인가? 전자를 선택했다면 정책 선택임을 밝히는 편이 좋다.
- **근거에서 시작 객체로의 연결:** 외부에서 문제가 확인된 증빙을 어떤 원장 시작점에 대응시키는지 서론 수준에서 한 번 연결할 필요가 있다.
- **상태 용어:** "사용", "소비", "중단", "제한", "차단"이 같은 것을 뜻하는지 구분한다. 디지털 기록의 후속 소비를 막는다는 중심 정의가 필요하다.
- **연구 질문:** 현재 질문은 넓지만 앞 문단으로 뒷받침된다. 전체 공급망 정보 관리가 아니라, 검증된 연결 복원과 현재 소비 차단의 결합에 초점을 좁힐지 논의한다.

## 1.3 선행연구와 본 연구의 과제

- **장점:** 기존 연구가 이미 제공하는 검증·추적·동결을 인정하여 과도한 최초 주장을 피한다.
- **아직 약한 부분:** "서로 대응해야 한다"는 필요조건은 설명하지만, 어떤 구체적 실패를 막는 대응인지 독자가 바로 보기 어렵다.
- **추가할 수 있는 연결:** 거래 proof에 결합되지 않은 감사 정보는 실제 전이와 다른 graph를 가리킬 수 있고, graph를 복원해도 소비 식별자와 연결되지 않으면 차단할 대상을 찾지 못한다는 문제를 서론 수준에서 설명할 수 있다. 이것이 기존 연구에 없는지 여부는 별도로 비교해야 한다.
- **Novelty 판단은 보류:** 이 절만으로 신규성을 입증했다고도, 신규성이 없다고도 결론 내리지 않는다. 2절의 비교와 실제 구성·정리 범위를 함께 봐야 한다.

## 1.4 zkDPP의 설계와 기여

- **강점:** 이미 발급한 Claim과 아직 차단 가능한 객체를 구분한다. 개별 Freeze 성공과 전체 완료도 구분한다.
- **첫 소개의 정보량:** 핵심 경로를 설명하기 전에 key wrapping·정족수·키 사본 관리·경합·조회 실패가 연속 등장한다. 개요와 세부 실패 조건을 어느 깊이까지 둘지 결정한다.
- **"전체"의 기준:** 어떤 시작점과 확정 시점에서 복원한 전체 집합인지 명시되어야 한다. 이후 생성된 모든 자손까지 자동 차단한다는 뜻은 아니다.
- **권한 흐름:** "사용 중단이 승인되면"의 승인 주체가 누구인지, 감사자 자신의 판단과 별도 승인인지 불명확하다.
- **두 contribution의 구분:** 첫 항목은 구성, 둘째는 보장 분석으로 나뉜다. 구현 실험을 포함한다면 검증한 범위에 맞는 별도 기여가 필요하다.
- **비교 대상으로 삼을 기여:** 회계·Claim·Traceability·Freeze 각각의 존재보다, 실제 전이와 추적 정보 및 소비 차단 식별자의 일치와 전체 완료 판정이 무엇을 더 보장하는지 명료하게 제시할 필요가 있다.
