# 실험 결과 보고서 작성 계획 — Markdown과 LaTeX

**무슨 동작을 실행했고, 어떤 조건에서 얼마의 비용이 들었으며, 그 결과로 어디까지 설명할 수 있는지를 두 형식으로 동일하게 전달합니다.**

대상은 [실험 우선순위와 측정 기준](experiment-priorities-and-criteria.md)의 8개 실험입니다. 이 문서는 결과를 작성하는 계획이며, 아직 수행하지 않은 실험의 수치를 채우지 않습니다.

## 1. 최종 산출물은 무엇인가요?

| 예정 파일 | 역할 |
|---|---|
| docs/experiment-results.md | 저장소와 대화에서 바로 읽는 결과 보고서 |
| docs/experiment-results.tex | 같은 내용을 문서로 조판하고 논문 작성에 활용하는 LaTeX 보고서 |

**두 파일은 같은 보고서의 두 표현입니다.** 목차, 실험·case 이름, 수치·단위, 측정 조건, 결론과 한계가 같아야 합니다. 어느 한쪽에만 핵심 설명을 넣지 않습니다. 각 파일만 읽어도 동작과 결과를 이해할 수 있게 합니다.

LaTeX는 단독으로 compile 가능한 문서로 작성합니다. 그래프가 필요하면 두 형식이 같은 결과 데이터에서 만든 그림을 사용하며, 공유 시 필요한 그림 파일도 함께 전달합니다. 검토용 PDF는 LaTeX 조판 확인에 사용하고 필수 결과 문서는 위 두 파일로 둡니다.

## 2. 기존 보고서에서는 무엇을 가져오나요?

[기존 POC Evaluation Report.tex](../../poc-v2/POC%20Evaluation%20Report.tex)는 **설명 구조와 조판의 참고**로 사용합니다. 현재 Protocol이나 성능 수치의 원본으로 사용하지 않습니다.

| 가져올 방식 | 그대로 가져오지 않을 내용 |
|---|---|
| 첫 화면의 목표·구현·측정 요약 | 과거 Event 수·profile 수·성능값 |
| 입력·출력과 Event 흐름을 연결한 시나리오 | 이전 State 순서·별도 quantity·epoch 관계 |
| 요약 결과와 개별 transaction 상세의 분리 | 과거 Process allocation·slot 모델 |
| 측정값 바로 뒤에서 원인을 설명 | 이전 Provenance·Recipe의 미해결 사항 |
| 재현 명령·Raw 연결 | 과거 반복 횟수·환경을 새 결과에 적용 |

새 보고서는 현재 **(q_mass, a_rec, e)** 순서, 9개 Event, Standard Issue를 사용합니다. Process는 실험용 2→1 기본과 2→2·3→2·3→3·4→3 구성을 사용합니다.

**기존 M1-HF의 WASTE 생성 3→2와 새 실험의 WASTE 없는 3→2는 다른 case**로 표시합니다. 과거 수치는 필요할 때만 별도 참고 열에 출처·조건과 함께 표시합니다.

[Result Template](../milestones/RESULT-TEMPLATE.md)의 correctness·측정 경계·실패·재현·checksum 요구는 유지하되, 본문은 Milestone 변경 이력이 아니라 실험의 우선순위로 구성합니다.

## 3. 보고서는 어떤 순서로 읽게 하나요?

### 먼저 결과를 이해할 기준을 보여줍니다

첫 화면에는 **실제로 완료한 기능, 수행한 실험, 대표 결과, 중요한 한계**를 짧게 보여줍니다. 코드 경로나 큰 Hash 값을 먼저 나열하지 않습니다.

그다음 공통 조건을 설명합니다.

- 대상 Protocol·실험 구현과 비교군의 차이
- 하드웨어·Proof system·Curve·Hash·Tree·SRS·Anvil 환경
- State 단위와 scale, 실제 반복 횟수·대표 통계
- Event E2E, 전달 경로 E2E, DPPClaim 검증, Tracing의 시작·종료점
- Split 대표 예시와 Process 실험 시나리오

이미 Note·cm·nf를 이해한 동료를 독자로 가정합니다. Protocol 전체를 다시 설명하지 않고, **결과 해석에 필요한 객체 전이·검사·온체인 변경만** 해당 실험 옆에 설명합니다.

### 결과 본문은 8개 우선순위와 일치시킵니다

| 번호 | 결과 절 | 필수 결과와 보여줄 형태 |
|---|---|---|
| 1 | Event 기본 성능·E2E와 DPPClaim 검증 | 9개 Event 결과표, 별도 DPPClaim 검증표, Setup·Policy 준비 비용표 |
| 2 | 직접 Transfer와 Voucher 전달 | 전달·수령·회수 경로 그림, 경로 전체 비용과 Proof·transaction 수 |
| 3 | 모든 Event의 Audit 추가 비용 | Event별 Audit 없음·있음·절대 차이·증가율 |
| 4 | Tracing·Freeze 확장성 | 실제 복원 graph·frontier·terminal, 규모별 시간·RPC·복호화·동결 수 |
| 5 | State·검증 관계 확장 | Claim 조건 비교와 State 개수 비교를 별도 표·그림으로 구분 |
| 6 | Process 입출력 확장 | 다섯 arity의 입력·출력 합계와 Audit 유무 비용, domain 변화 |
| 7 | 감사 암호문 복호화 | 암호문 수 변화와 Field 수 변화를 분리한 시간·allocation 결과 |
| 8 | Master Key 복구 | k 변화와 n 변화를 분리한 검사·보간·공개키 대조 비용 |

마지막에는 **결론·실패와 한계·재현 정보**를 둡니다. 개별 transaction 목록, 전체 반복값, Artifact checksum은 부록으로 보냅니다. 본문에서 부록을 열지 않아도 주요 결과를 이해할 수 있어야 합니다.

## 4. 각 실험은 어떤 문장 순서로 설명하나요?

**질문 → 실행 조건 → 실제 결과 → 해석 → 한계**를 같은 순서로 사용합니다.

| 순서 | 반드시 답할 내용 |
|---|---|
| 질문 | 어떤 기능의 비용이나 확장성을 확인하려 했는가? |
| 실행 조건 | 어떤 동작을 실행했고, 무엇을 고정하고 무엇을 바꿨는가? |
| 실제 결과 | correctness는 통과했는가? 측정값과 반복 수는 무엇인가? |
| 해석 | 함께 기록한 constraints·RPC·저장량으로 무엇을 설명할 수 있는가? |
| 한계 | 무엇을 분리하지 못했으며, 어느 범위 밖으로 일반화하면 안 되는가? |

**성공 사실, 관찰한 수치, 원인 해석을 한 문장에 뭉치지 않습니다.** 결과를 먼저 보여주고 해석을 이어갑니다. 원인을 직접 분리하지 못했다면 확정적인 원인으로 쓰지 않습니다.

예를 들어 Tracing에서는 기록 수별 총시간·고유 기록·RPC·복호화 수를 먼저 제시합니다. 그 뒤 관찰한 증가 경향을 설명합니다. 두 측정점만 보고 “항상 선형”이라고 결론 내리지 않습니다.

전달 비교에서는 추가 Proof·transaction·Voucher Tree 변경을 제시한 뒤 비용 차이를 설명합니다. 수령 후 소비 Privacy는 설계·보안 분석의 결과이며, 전달 시간이 증가했다는 사실로 증명하지 않습니다.

## 5. 숫자의 의미와 출처는 어떻게 고정하나요?

### 같은 데이터와 같은 집계 규칙을 사용합니다

**Raw 결과 → case별 대조·집계 → Markdown 본문과 표 → 같은 내용의 LaTeX 조판** 순서로 작성합니다.

Markdown을 내용 검토의 기준으로 두되 수치의 근거는 Raw입니다. LaTeX에서 숫자·결론을 별도로 고치지 않습니다. 수정이 필요하면 Raw 근거와 집계부터 대조하고 두 형식을 함께 갱신합니다. 별도 YAML 모델이나 범용 문서 변환 시스템은 만들지 않습니다.

각 표·그림의 데이터는 다음으로 역추적할 수 있어야 합니다.

- experiment·case·run 식별자와 성공·실패 여부
- source·Circuit·Policy·SRS·PK/VK 식별정보
- 입력 규모·선행 원장 상태·cache 조건
- 타이머 시작·종료, 단위, 실제 반복 횟수
- Raw 경로·필드와 checksum, 사용한 집계·반올림 규칙

본문의 표 아래에는 **case, 단위, 반복·통계, 측정 경계, Raw 출처**를 짧게 적습니다. 긴 checksum과 개별 실행 목록은 부록에 둡니다. 서로 다른 시나리오 안의 같은 Event들을 이유 없이 하나의 대표값으로 합치지 않습니다.

### 증가량과 증가율은 비교군을 기준으로 계산합니다

$$
\Delta C=C_{\mathrm{with}}-C_{\mathrm{without}}
$$

$$
\mathrm{increase}(\%)=100\times\frac{\Delta C}{C_{\mathrm{without}}}
$$

C는 같은 단위·측정 경계의 비용입니다. 반올림 전 값으로 계산합니다. 분모가 0이거나 직접 전달의 Recall처럼 대응 기능이 없으면 증가율은 **해당 없음**으로 표시합니다. 음수 차이도 숨기지 않고 원인을 검토합니다.

### 혼동하기 쉬운 측정값을 구분합니다

| 구분 | 보고서 표기 원칙 |
|---|---|
| Event E2E와 단계별 시간 | 전체 구간을 직접 측정한 값만 E2E로 표시 |
| 로컬·온체인·DPPClaim Verify | 세 작업을 서로 다른 이름으로 표시; 로컬 PLONK Verify는 보조 결과 |
| Setup·배포와 Event 실행 | 일회성 준비 비용을 반복 실행 비용에 중복 합산하지 않음 |
| 총 gas와 SSTORE | SSTORE opcode 비용은 전체 gas와 별도 표시 |
| AuditRecord·암호문·Field | Split은 감사 암호문 1개·Field 3개; 기록 metadata는 별도 |
| frontier와 Freeze transaction | 이미 차단된 target은 새 transaction이 없을 수 있음 |
| 누적 메모리 할당량과 peak RSS | 실제 측정한 메모리 지표 이름과 단위 유지 |
| 반복과 workload | 암호문 1,000개를 처리한 1회 실행을 반복 1,000회로 쓰지 않음 |

하나의 실행을 여러 표에 사용하면 같은 case·run ID를 표시합니다. 단일 실행에는 반복 실험의 표준편차나 안정성을 붙이지 않습니다. 미측정·미구현·실패·해당 없음을 0이나 빈칸 하나로 합치지 않습니다.

## 6. 표·그림과 문장은 어떻게 읽기 쉽게 만드나요?

- **표 하나는 질문 하나에 답합니다.** Event의 시간표와 저장·gas 표는 폭이 넓어지면 나눕니다.
- 경로 그림은 직접 전달과 Transfer→Proceed, Transfer→Recall을 구분하는 데 사용합니다. 두 분기를 한 실행으로 합치지 않습니다.
- 확장성 그래프는 x축의 변경 변수와 y축의 단위를 명시합니다. 다른 단위의 비용을 한 축에 섞지 않습니다.
- 입력·출력 크기를 같이 표시하되, 인접 비교에서 무엇이 증가했는지 caption에 적습니다. domain 경계도 표시합니다.
- 결과를 설명하는 문단은 첫 문장에 관찰한 결과를 제시하고, 다음 문장에서 근거와 해석을 설명합니다. 한 문장에 조건·결과·예외를 모두 넣지 않습니다.
- 핵심 결론과 비교 조건에는 Bold를 사용합니다. Event·Audit·Freeze 같은 고유 용어와 cm·nf·PolicyRef 같은 핵심 변수는 원문 표기를 유지합니다.
- “A”, “이 값”, “위 기록” 대신 cm_A·해당 Issue 기록처럼 대상을 명시합니다.
- 같은 수치의 표와 그래프를 모두 넣을 때는 각각의 역할이 달라야 합니다. 장식용 그림과 긴 Raw 배열은 넣지 않습니다.

### Markdown

자연스러운 한국어 제목, 짧은 문단, 표, 수식으로 구성합니다. 코드 블록은 재현 명령 등 꼭 필요한 곳에만 사용합니다. 링크는 근거 확인용이며 핵심 설명을 다른 파일로 넘기는 용도로 사용하지 않습니다.

### LaTeX

기존 보고서처럼 A4·11pt 본문·KoTeX·수식 패키지·booktabs 계열 표를 기본으로 합니다. 긴 표는 longtable로 분리하고 열 제목을 반복합니다. 표를 맞추려고 본문·표 글자를 과도하게 줄이지 않습니다.

주요 설정은 문서 안에 둡니다. 한글·수식·URL·표 너비를 실제 compile로 확인합니다. 제목에 완료일·기준일은 넣지 않습니다. 필요한 측정 시각은 재현 정보의 run 기록으로 관리합니다.

## 7. 어떤 순서로 작성하고 검토하나요?

1. **실험 완료 확인:** 각 case의 correctness·Raw·실패 이력·측정 범위를 점검합니다.
2. **표 먼저 대조:** 동일 조건끼리 묶고 단위·반복 수·증가율을 확인합니다. 아직 없는 값은 미측정으로 둡니다.
3. **Markdown 작성:** 8개 실험마다 질문·실행·관찰·해석·한계를 작성합니다.
4. **논리 검토:** SubAgent가 수치 근거, 비교군, 타이머, 성공 판정과 결론의 범위를 검토합니다.
5. **독자 관점 검토:** 다른 SubAgent가 모호한 대명사, 긴 문장, 설명의 비약, 중복·불필요한 부가정보를 검토합니다.
6. **LaTeX 작성:** 검토된 Markdown과 같은 내용·표·수식·그림으로 조판합니다.
7. **형식 대조:** 두 문서의 case 수·수치·단위·caption·결론을 Raw와 교차 확인합니다.
8. **시각 확인:** LaTeX를 compile하고 PDF의 모든 페이지에서 한글·수식·표 넘침·잘림·링크를 확인합니다. Markdown도 수식·표·그림·링크의 렌더링을 확인합니다.

문서 검사를 위해 성능 benchmark를 다시 실행하지 않습니다. 누락된 측정이 발견되면 해당 case를 별도 실행·이력으로 남긴 뒤 반영합니다. 실패한 시도를 삭제하고 성공 한 번으로 표현하지 않습니다.

## 8. 언제 완료 보고서로 표시하나요?

- 8개 실험의 필수 case와 DPPClaim 확인 결과가 있으며, 주장하는 모든 수치가 Raw로 연결됩니다.
- 미완료 항목이 있으면 전체 완료가 아니라 부분 완료로 표시합니다. 미측정 항목은 결론에서 제외합니다.
- 같은 Policy·입력·환경의 비교인지, 함께 바뀐 조건이 있는지 설명합니다.
- Process 실험용 합계 (300,30,261)과 기존 WASTE 시나리오를 구분합니다.
- Tracing·복호화·키 복구를 구분하고, Freeze 판정은 공통 checkpoint의 Note·Voucher target에 한정합니다.
- 개발 SRS, Anvil 환경, 고정 share와 DKG 미구현 등 적용 한계를 명시합니다.
